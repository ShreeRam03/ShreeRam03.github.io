Building a mini-SIEM for login attacks

A SIEM collects logs and runs correlation rules over them: "if this many failures happen from one IP in this many minutes, raise an alert". I wanted to understand those rules properly, so I wrote a small version myself. It reads Linux auth.log files and Windows Security events, and flags the login patterns an L1 SOC analyst is expected to catch.

The story in the logs

The sample logs in the repo tell one short attack story, using documentation IP ranges and fake hosts:

10:15Brute force203.0.113.50 fails 8 times against root in about a minute.
10:16Break-inThe 9th attempt succeeds.
10:18PersistenceA new account, sysupdate, appears.
13:40SprayingAnother IP tries admin, test, oracle, ubuntu and guest.

On the Windows side, Administrator is brute-forced and a new account is added to an admin group. The tool turns all of that into 8 alerts: 4 High, 3 Medium, 1 Low.

The detection rules

Each rule is a short Python function with its threshold in the signature, so it's easy to read and tune:

  • Brute force (T1110.001): 5 or more failures from one IP within 10 minutes, against 1 to 3 accounts.
  • Password spraying (T1110.003): one IP failing against 4 or more different accounts.
  • Login after repeated failures (T1078): a success from an IP that just failed 3 or more times. This is the alert that matters most, because it may mean the password was guessed.
  • New account (T1136.001) and added to an admin group (T1098): classic persistence after a break-in.
  • Off-hours login (T1078): a successful login between midnight and 5 am.

Teaching it to stay quiet

My first run flagged the spraying IP twice: once as spraying and once as brute force, because its 5 failures also fell inside 10 minutes. Two alerts for one event is noise, so brute force now only fires when the failures target 1 to 3 accounts, and anything wider is left to the spraying rule.

The sample log also has a user, alice, who mistypes her password once and then logs in. That must not raise an alert, and there is a unit test that fails if it ever does.

What I learned

  • Thresholds are decisions. "5 in 10 minutes" is a choice someone has to justify and tune; it isn't a fact.
  • Duplicate alerts cost analyst time. One event should produce one clear alert.
  • Mapping to MITRE ATT&CK helps the next person. T1110.003 tells a colleague what happened faster than a paragraph does.
